# Contributing

This guide is for contributors and maintainers. For install and usage, see [README.md](README.md).

This is an **unofficial, community-maintained** Flatpak of the proprietary Grok Bot. It is not endorsed, published, or supported by the Grok Bot vendor. Contributions must stay inside that scope: packaging, integration, and automation in this repository. Never scrape vendor pages, redistribute upstream binaries outside the pinned artifact flow, or present this package as official.

## Quick path

1. Open an issue with the [bug report](.github/ISSUE_TEMPLATE/bug-report.yml) or [feature request](.github/ISSUE_TEMPLATE/feature-request.yml) form. Search open and closed issues first, and never include credentials, tokens, or authentication callbacks.
2. Make the change on a branch and open a pull request against `main`. Pull requests run the `validate` workflow and must pass before merge.
3. Verify locally with the workspace gate before pushing:

```bash
python3 tools/test.py
```

## Pull requests

Open a pull request against `main` from a `type/description` branch (for example `fix/tray-regression`). Fill in [`.github/PULL_REQUEST_TEMPLATE.md`](.github/PULL_REQUEST_TEMPLATE.md): link an approved issue (`Closes #N`, issue carries `status:approved`) and pick exactly one type label:

| PR type | Label |
|---------|-------|
| Bug fix | `type:bug` |
| New feature | `type:feature` |
| Documentation only | `type:docs` |
| Code refactoring | `type:refactor` |
| Maintenance/tooling | `type:chore` |
| Breaking change | `type:breaking-change` |

Record the `python3 tools/test.py` result plus focused or runtime evidence, and name the rollback boundary. Pull requests run the `validate` workflow and must pass before merge. Use Conventional Commits with no `Co-Authored-By` trailers. Keep the change at most 400 changed lines, or get maintainer approval for `size:exception`.

## Prerequisites

| Need | Requirement |
|------|-------------|
| Workspace gate | `python3`, `cmake`, and `ctest` on `PATH` |
| Companion build (always ON) | Qt6 Widgets/DBus, KF6StatusNotifierItem, KF6WindowSystem; missing deps fail the gate closed |
| Payload build (optional) | `flatpak-builder` plus Flathub `org.kde.Platform//6.11` and `org.kde.Sdk//6.11` |

## Workflow

- The gate is fail-closed: Python unittest discovery plus CTest must both pass. Zero tests, missing tools, missing Qt6/KF6 deps, or a skipped layer fails. It compiles the companion, downloads no AppImages, and proves no X3.
- The companion defaults ON (`GROK_BOT_BUILD_COMPANION` defaults ON and the gate forces it ON). Configure and build it locally with:

```bash
cmake -S . -B build
```

  `-DGROK_BOT_BUILD_COMPANION=OFF` is a developer-only configure escape (supported by the root `CMakeLists.txt` option) and does not satisfy the workspace gate — CI runs the unchanged gate inside `org.kde.Sdk//6.11`.

- A full payload build is optional and dual-arch (`x86_64` and `aarch64`):

```bash
flatpak-builder --force-clean --repo=repo build-dir io.github.viniciosrab.GrokBot.yml
```

- Graphical X3 proof (`bash tools/prove_x3.sh`) needs a hosted KDE session with Xvfb, a real `plasmashell`, and `kactivitymanagerd`. It is expensive and never a local default; the headless watcher rejection in `validate` is a negative test, not X3 proof.

## Boundaries

- `data/pins.yml` is generated by the six-hour pin job from the two sand feeds. Do not edit it by hand. Pin changes touch only `data/pins.yml`, `io.github.viniciosrab.GrokBot.yml`, and `data/io.github.viniciosrab.GrokBot.metainfo.xml`.
- Nothing pushes directly to `main`; automated pin updates arrive as `pin/sand-*` branch pull requests gated by required checks.
- Keep the closed finish-args set, the KDE 6.11 runtime, and the zypak module as-is. Never add an Electron BaseApp base or a `nickle` path overlay.
- The tray icon contract and the padded taskbar/window icon contract are covered by tests; do not reroute either path.

## Conventions

- Write code, comments, docs, and commit messages in English.
- Use Conventional Commits (`fix(scope): ...`, `chore(scope): ...`), matching repository history.
- Do not commit `build-dir/`, `repo/`, `.atl/`, `.codegraph/`, or `__pycache__/`.

## Releases

Ordinary pushes to `main` validate but never auto-publish, including docs-only changes. A genuinely new upstream version from the pin job traverses validate, dual-arch X3 proof, and publish automatically; same-version repins no-op. Same-version packaging republishes run only through a manual `publish` dispatch from `main` with the required `reason` input:

```bash
gh workflow run publish.yml --ref main -f reason="why this republish is needed"
```

Publication signing uses the `GPG_KEY` secret and the pin automation uses `APP_ID` / `APP_PRIVATE_KEY`. Names are listed here so contributors know which settings exist; values are never shared or committed.
